# 我们的小日子 · 独立服务器版

此部署包同时提供网页和后端。需要 Node.js 22.18 或更新版本（推荐 24 LTS）；
运行时只使用 Node 内置模块，不需要 npm 安装、Cloudflare、ChatGPT 登录或云数据库。
首位成员拥有账号管理、完整备份和恢复权限；第二位成员使用自己的密码。

## 从 GitHub 源码构建

若拿到的是本仓库源码而不是已构建部署包，先运行：

```sh
git clone https://github.com/liu7866/couple-home.git
cd couple-home
pnpm install --frozen-lockfile
pnpm run build:node
pnpm run test:node
```

构建需要 pnpm 11.25.0。构建成功后，只需将 `dist-node/`
中的内容复制到服务器版本目录，服务器运行时不需要 node_modules。
下文中的 `admin.mjs`、`server.mjs`、`deploy/` 均相对于该构建产物的根目录。
若只想启动本机完整源码目录，运行 `pnpm run start:node`，在首次打开的页面设置密码即可。

## 本地试用

1. 将部署包解压到一个空目录，安装上述版本的 Node.js。
2. 复制 `.env.example` 为 `.env`，本地配置默认监听 `127.0.0.1:3000`。
3. 运行 `node --env-file-if-exists=.env server.mjs`，也可在 Windows 双击 `start.cmd`。
4. 打开 http://127.0.0.1:3000 ，首次页面直接设置并确认两位成员的密码（6 至 128 个字符）。
   创建后自动以成员一登录并打开“布置小屋”；成员一拥有管理员权限，成员二使用自己的密码登录。
5. 默认身份名称为“成员一、成员二”。管理员可在「布置小屋 → 修改身份名称」中自定义，
   登录选择框随之更新；名称会显示在登录页，不改变密码和管理员归属。

如果习惯终端初始化，仍可使用 `node --env-file-if-exists=.env admin.mjs init`。
已经创建的账号不会被首次页面再次初始化，也不会覆盖已有回忆。
已有小屋的登录页可点“设置 / 找回密码”查看密码管理方法；有个人恢复码时可直接验证后设置新密码。

默认数据保存在部署目录下的 `data/`。这里是真实持久化数据，不是演示数据；
停止服务再启动仍会保留。此版本不会读取原先 `.wrangler/` 内的开发数据。
请勿覆盖或删除 `data/`；更新时应使用独立的绝对数据路径。

## 阿里云 Linux 部署

下面示例使用带 systemd 的 Ubuntu/Debian 系统，Node.js 已安装在 `/usr/bin/node`。
请先确认 `node --version`。如果 Node 在其他位置，修改两个 `.service` 的 ExecStart。
使用实际域名、HTTPS 证书和可访问该网站的网络配置。

1. 解压部署包到 `/opt/little-days/releases/一个版本号/`，将
   `/opt/little-days/current` 软链接指向该目录。保留旧版本，方便回退。
2. 创建独立服务用户和持久化目录（管理员终端）：

```sh
sudo useradd --system --home-dir /var/lib/little-days --shell /usr/sbin/nologin little-days
sudo install -d -m 700 -o little-days -g little-days /var/lib/little-days /var/backups/little-days
sudo cp /opt/little-days/current/deploy/environment.example /etc/little-days.env
sudo chown root:little-days /etc/little-days.env
sudo chmod 640 /etc/little-days.env
sudoedit /etc/little-days.env
```

把 `/etc/little-days.env` 设置为以下内容（域名替换成自己的）：

```dotenv
HOST=127.0.0.1
PORT=3000
APP_ORIGIN=https://your-domain.example
TRUST_PROXY=1
DATA_DIR=/var/lib/little-days
BACKUP_DIR=/var/backups/little-days
```

3. 创建账号。密码在终端提示时输入，不写到命令行参数或环境文件中：

```sh
cd /opt/little-days/current
sudo -u little-days /usr/bin/node --env-file=/etc/little-days.env admin.mjs init
```

这一步也可以留到服务启动后在网页上完成：公网 HTTPS 的首次设置需要小屋初始化码，
部署者通过 `sudo journalctl -u little-days.service` 在服务启动日志中查看并私下提供。
自动生成的码保存在 DATA_DIR 的 `.setup-code` 文件（仅服务用户可读）；也可以在私有环境文件中
指定 24 至 128 个字符的 SETUP_CODE。初始化码不会返回给访客，已有小屋不能再次初始化。
本机回环 HTTP 预览无需该码；反向代理后的 HTTPS 站点仍需该码，不因代理连接来自本机而免除。

4. 安装并启动服务与定期备份：

```sh
sudo cp deploy/little-days.service deploy/little-days-backup.service deploy/little-days-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now little-days.service
sudo systemctl enable --now little-days-backup.timer
sudo systemctl status little-days.service
```

5. 将 `deploy/nginx.conf.example` 按实际域名和证书路径配置到 Nginx。
   运行 `sudo nginx -t` 通过后重载 Nginx。通过 HTTPS 域名访问网站。
   应用端口 3000 只监听本机，外部访问使用 Nginx 的 80/443 端口。
   `TRUST_PROXY=1` 只信任来自本机回环地址的 `X-Real-IP`，不会信任外部自报的 Cloudflare 用户头。

6. 检查域名首页、两位成员登录、照片上传、下载备份，以及服务重启后的数据。
   反向代理健康检查可访问 `/healthz`；它不返回私人数据。

HTTP 仅允许 localhost/回环地址，正式站点必须设置 HTTPS 来源。
`APP_ORIGIN` 不带路径或末尾斜线，且必须与浏览器地址完全一致。
第一版前后端部署在同一域名，不支持把此版前端直接放到另一个 GitHub Pages 来源。

## 数据迁移

此前取回的是源码。原站的 D1 记录和 R2 照片没有自动进入本部署包。
在原站由管理员下载「完整备份」，在新站使用第一位成员账号登录，
打开「导入回忆」，预览后选择合并或恢复。
先把旧站的完整备份确认保存好，再开始迁移；确认新站照片和记录完整后再决定旧站如何处理。
密码、登录会话与恢复码不包含在页面完整备份内，需要在新站重新设置。

## 备份与恢复

页面中的完整 JSON 备份可保留记录与照片，支持跨版本导入。
服务器还提供带数据库和照片校验的快照：

```sh
node --env-file-if-exists=.env backup.mjs
node backup.mjs --verify /备份/快照目录
```

Linux 服务使用相同命令并加 `--env-file=/etc/little-days.env`，以 little-days 用户运行。
定时器每天服务器时间 02:30 左右执行。可用
`systemctl list-timers little-days-backup.timer` 和
`journalctl -u little-days-backup.service` 检查，未自动清理旧备份。
备份期间数据库写操作会短暂等待；失败不生成 `complete.json`，不算有效备份。
照片遗失时会明确失败，不会把残缺备份标记为完成。

服务器快照包含密码哈希、会话和未到期信件，必须私下保管。
本机备份不能抵御服务器磁盘整体损坏，请另存到自己的其他设备或私有存储。

恢复服务器快照时，先校验快照并停止 little-days 服务，把快照的 `home.sqlite`
和 `photos/` 复制到一个**新的空数据目录**，调整所有者与权限，再将 DATA_DIR 指向新目录。
保留原数据目录，重新启动服务确认。不要把快照覆盖到含旧 WAL/SHM 文件的运行中数据库上。
随附 systemd 服务的可写路径是 `/var/lib/little-days`；新目录可使用该目录下的空子目录。如使用其他路径，必须同时调整主服务与备份服务的 `ReadWritePaths`，并确认实际权限。

## 找回密码与更新

网页支持 12 位个人恢复码。管理员可在「密码与恢复码」中生成，两位成员分别保存。界面每 4 位分组，输入时可使用小写、空格或分隔线；旧的 64 位恢复码仍有效，使用或重新生成后换成短码。成员密码最少 6 个字符。
服务器管理员也可以运行：

```sh
node --env-file-if-exists=.env admin.mjs reset-password
```

按提示选择成员、输入新密码。此操作使对应成员的旧会话和恢复码失效，不改动回忆。
初始化命令不允许覆盖已有账号。自动化工具可显式加 `--stdin` 输入 JSON：
初始化格式为 `{"names":["名字一","名字二"],"passwords":["密码一","密码二"]}`；
重设格式为 `{"slot":1,"password":"新密码"}`。不要将真实密码放入公开脚本或 shell 历史。

更新前先完成一次快照，再解压新版本、切换 current 链接、重启服务。
数据路径保持不变。已有 SQL 迁移保持原样；启动会校验并应用新增迁移。
若未来版本改变数据库结构，回退代码前需确认兼容性，必要时恢复更新前的快照。
